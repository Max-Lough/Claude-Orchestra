# Orchestra 2.0 Harness Value Oracle

## VERDICT

**PARTIAL at the component level; NO for the current 2.0 system as a whole.** Orchestra 2.0 contains two benefits that a prompt-only harness cannot fully supply: a pinned, cross-vendor execution substrate and machine-replayable evidence about what ran, changed, and was reviewed. Those are real. The ticket gate, 23-class taxonomy, Router, two-call close protocol, and Quartermaster have not shown a net benefit over the legacy `ORCHESTRA.md` plus focused agent definitions. On the available live evidence they make frontier models slower, harder to recover, and easier to strand in harness state without demonstrating better delivered work.

The go/no-go answer is therefore **no-go for another 2.0 architecture revision**. Restore 1.0 as the operating system and port only the narrow evidence and cross-vendor capabilities listed below. If the owner allows one final test, it should be a frozen, slim candidate against a measured legacy control, not another repair wave. Missing comparison data must count against 2.0, because generating trustworthy comparison data was one of the control plane's jobs.

The owner's diagnosis is substantially right: the current system is over-engineered relative to its demonstrated value. The owner would be wrong only if that conclusion were broadened to “nothing here is useful.” Independent cross-family execution, immutable run identity, tree-diff capture, and deterministic mechanical checks are useful precisely because they do not rely on a model remembering protocol text. They do not require the rest of 2.0.

## FINDINGS

1. **[CRITICAL] 2.0 has not cleared its own acceptance gates, and the live run is negative evidence rather than merely absent evidence.** The design says activation requires evidence-backed semantic review, sufficient review capacity, seeded-defect recall, escape performance no worse than baseline, bounded allowance draw, and routing recovery (`plans/cross-compare/agent-role-architecture/final-plan.md:1723-1760`). The September 1-2 ledger instead records 93 tickets and 11h25m of summed active time, with a list-price proxy of $105.42 that explicitly omits the actual Codex engine usage (`.claude/scratch/oracle/ppp-ledger-report-2026-09-01-to-02.txt:1-2`, `tools/orchestra-ledger-report.js:1-23`). I count only 5 `CLOSED` outcomes among 45 builder tickets in the ticket table; 35 builder tickets remain merely `RESOLVED` (`.claude/scratch/oracle/ppp-ledger-report-2026-09-01-to-02.txt:4-306`). The anomaly section contains 42 “RESOLVED but never CLOSED” rows (`.claude/scratch/oracle/ppp-ledger-report-2026-09-01-to-02.txt:341-477`). Of 25 reviewer tickets, only 16 verdicts parsed, only 11 had mechanical audits, and only 5 of those audits passed; reviewer launchers alone consumed 4h27m, about 39% of summed active time (`.claude/scratch/oracle/ppp-ledger-report-2026-09-01-to-02.txt:307-334`). The 136 anomaly rows are not 136 independent bugs—the report deliberately includes expected intermediate and refused states—but they still show that the normal lifecycle was not closing cleanly (`tools/orchestra-ledger-report.js:358-371`).

2. **[MAJOR] The control plane adds roughly an order of magnitude more mechanism than the protocol it replaces, while leaving the hard judgments with the caller.** A read-only physical-line count gives 17,865 JavaScript lines across the 18 in-scope 2.0 implementation files under `bridge/`, `router/`, `registry/`, `verifier/`, `quartermaster/`, `hooks/`, and `packs/codex/hooks/`. The current `ORCHESTRA.md`, `agents/`, and `skills/` total about 714 lines—and that is a conservative comparator because the current `ORCHESTRA.md` already contains 2.0 additions. Yet dispatch still requires the model to supply the class, risk, scope, acceptance, and file hints (`registry/README.md:25-44`); the runtime then enforces a fresh P0 reading before it will dispatch (`bridge/runtime.js:356-425`). This is enforcement around judgment, not replacement of judgment. Enforcement is valuable for a few safety invariants, but not enough to justify a permanent 25x implementation footprint and its operating surface.

3. **[MAJOR] The class/casting architecture failed its empirical validation and was retained as a hypothesis.** The four blinded classification rounds scored 31/40, 17/20, 16/20, and 14/20; every formal gate failed (`plans/cross-compare/agent-role-architecture/final-plan.md:1861-1878`, `plans/cross-compare/agent-role-architecture/final-plan.md:1880-1898`, `plans/cross-compare/agent-role-architecture/final-plan.md:1916-1925`, `plans/cross-compare/agent-role-architecture/final-plan.md:1960-1970`). The owner then ended the cycle and allowed class to survive only as a recoverable routing hypothesis (`plans/cross-compare/agent-role-architecture/final-plan.md:1977-2003`). The implementation subsequently retired or merged twelve roles and reduced the active roster to eleven (`router/README.md:34-60`). That correction is sensible, but it is also evidence that a detailed taxonomy was not granting modern models a stable capability advantage. A frontier Director can choose “investigate, build, or review” from a short protocol without a 23-class registry.

4. **[CRITICAL] The harness created a large, owner-visible failure surface before completing one clean lifecycle.** The shakedown records missing/non-blocking gates that allowed unticketed launches, inability to close recon, branch checkouts that removed tracked harness files, a direct-dispatch crash, a plain install silently downgrading `new` to `legacy`, lost telemetry, a Stop-hook loop of roughly 40 identical blocks, and stale-branch config invalidation (`roster/wo14b-shakedown-punch-list.md:13-23`). It then records four delivered work orders with no usable ledger telemetry because close was unreachable on four separate axes, followed by the first successful close only after another five same-day fixes (`roster/wo14b-shakedown-punch-list.md:24-31`, `plans/cross-compare/agent-role-architecture/STATUS.md:961-975`). PL30's Godot/Steam orphan-process incident was an environment failure, not fair evidence against the harness (`roster/wo14b-shakedown-punch-list.md:36`). Excluding it does not change the conclusion: the control plane repeatedly became the task.

5. **[MAJOR] Current cost and latency accounting does not support the economic rationale.** The live role totals show 18 investigator tickets at a $49.28 API-price proxy, 45 builder tickets at $51.75, and 25 OpenAI-reviewer launchers at $2.91—but the last number excludes the Codex engine itself (`.claude/scratch/oracle/ppp-ledger-report-2026-09-01-to-02.txt:307-318`). The same report records four requested/served-model mismatches, 21 unknown engine run nonces, six failed verdict audits, and 11 verifier `FAIL`/`REFUTED` rows in its anomaly section (`.claude/scratch/oracle/ppp-ledger-report-2026-09-01-to-02.txt:341-477`). The recorded pool readings fell 18 points for Fable and 10 for OpenAI in the period (`.claude/scratch/oracle/ppp-ledger-report-2026-09-01-to-02.txt:335-339`). These readings are not controlled cost measurements, and summed active time overlaps concurrent tickets (`tools/orchestra-ledger-report.js:386-401`), but every limitation makes the claimed savings less established, not more.

6. **[MAJOR] Independent review has real value, but the evidence supports a narrow cross-family lane rather than universal orchestration.** Earlier calibration found 10 of 12 sampled review findings real, though severity was inflated (`plans/cross-compare/agent-role-architecture/STATUS.md:65-90`). The verifier review sequence found repeated substantive defects; notably, `r0-ex5` identified a critical unsafe recursive-deletion path (`roster/r0-ex5-verdict.md:4-19`). In the live ledger, no `REVISE` verdict containing major-or-worse findings lacked replayable evidence (`.claude/scratch/oracle/ppp-ledger-report-2026-09-01-to-02.txt:320-334`). Those are genuine assurance wins. But legacy already requires a fresh reviewer, independent test execution, and batched review (`ORCHESTRA.md:50-68`, `ORCHESTRA.md:86-95`, `agents/reviewer.md:13-19`). What 2.0 uniquely adds is cross-vendor isolation and machine-bound evidence, not the idea of review. The prior oracle found no measurement of incremental cross-family recall and found review over-deployed (`roster/wo14b-review-protocol-oracle-2026-09-02.md:7-25`). Version 2.5 corrected the universal-review policy bug only on the day of this ledger (`CHANGELOG.md:12-69`), so the present run does not establish the corrected policy's steady-state value.

7. **[MAJOR] The Verifier is a useful tool but an unproven universal gate.** Its proper scope is narrow and sound: check deterministic facts, use a disposable writable checkout, and refuse to turn mechanical facts into a semantic verdict (`verifier/README.md:1-59`). In practice, close and claimed-change parsing produced false negatives, missing casting records, and empty-range review launches (`roster/wo14b-shakedown-punch-list.md:37-45`). The verifier/router tranche needed nine sequential cross-vendor verdict rounds before approval (`roster/r0-ex3-verdict.md:14-19`, `roster/r0-ex4-verdict.md:16-20`, `roster/r0-ex5-verdict.md:4-19`, `roster/r0-ex6-verdict.md:17-20`, `roster/r0-ex7-verdict.md:18-24`, `roster/r0-ex8-verdict.md:16-20`, `roster/r0-ex9-verdict.md:17-21`, `roster/r0-ex10-verdict.md:17-20`, `roster/r0-ex11-verdict.md:3-16`). That sequence demonstrates the reviewer lane's usefulness, but it also shows that much of the caught risk was created by making verification a stateful orchestration subsystem. Preserve the checks; remove them from every-agent lifecycle control.

8. **[MAJOR] Quartermaster does not currently provide the resource optimization used to justify it.** Its own documentation says the telemetry cannot attribute usage by role/effort/vendor/bucket and does not capture OpenAI engine consumption (`quartermaster/README.md:79-100`). Its forecast can be based on two points, is explicitly low-confidence, and does not persist prediction history (`quartermaster/README.md:347-370`). Ledger maintenance and cost reporting are declared unimplemented, while readings must be recorded and published manually (`quartermaster/README.md:428-475`). A manual, stale-prone number that can fail closed at dispatch is worse than a Director seeing the platform's actual usage and choosing a cheaper model. Until real vendor usage APIs exist, Quartermaster is policy theater with an outage mode.

9. **[MAJOR] The development opportunity cost is already disproportionate to the demonstrated benefit.** Read-only history contains 351 commits since August 27 (322 excluding merges); subject matching finds 88 WO-12 and 104 WO-14 commits, with overlaps excluded from the total but possible among topic counts. The original cross-comparison ledger records two aborted starts, then roughly three hours of drafting, critique, revision, synthesis, and support before implementation (`plans/cross-compare/agent-role-architecture/ledger.md:3-39`). The changelog then records repeated instrument, sandbox, classification, review, and activation repairs and explicitly says no v2.3 trial pass had run (`CHANGELOG.md:176-260`). That work produced useful lessons, but sunk cost is not a reason to keep a runtime architecture. Frontier models improve the economics of concise intent and independent checking; they do not improve the economics of debugging a second workflow engine around every task.

10. **[MINOR] The legacy protocol already captures most model-level benefits that survive contact with modern frontier agents.** It separates reconnaissance, execution, and review; requires self-contained orders; encourages parallel independent work; defines stop conditions; batches review; and scales the executor to task size (`ORCHESTRA.md:36-68`, `ORCHESTRA.md:86-125`). These are the parts that improve a frontier model's context, focus, and independence. A short protocol cannot guarantee provenance or prevent a model from bypassing it, but the evidence does not show that ordinary work needs a fail-closed authorization system for every subagent call. The correct boundary is: prompts for work decomposition and role behavior; small tools for facts a model cannot honestly attest to itself.

## WHAT 2.0 SUCCESS WOULD REQUIRE

“It finally closes tickets” is not success. Success means a smaller mechanical layer produces a material advantage over legacy on matched work without becoming work itself. One last test is defensible only under all of these conditions:

1. **Freeze before testing.** No harness code, prompt, install, manifest, parser, or model-map changes during the trial. Any repair or reinstall needed after the first task is a failed trial, not a reason to reset the clock. Do not implement PL39 microbatching or another close contract first; the punch list itself says to defer it until review share is known (`roster/wo14b-shakedown-punch-list.md:45`).
2. **Use a measured control.** Run the same 10-12 representative T1/T2 change packets, or faithful isolated replays, through legacy and the slim candidate with the same primary models, review policy, repository state, and acceptance tests. Add passive telemetry to legacy so both arms expose elapsed time, model turns, Director actions, provider usage, escaped defects, and adjudicated reviewer findings. Randomize order where state permits.
3. **Require operational invisibility.** Zero harness-induced denials, wrong-model service, lost reports, forced reinstalls, unknown nonces, branch/config invalidations, or dangling processes. At least 95% of structured verdicts must parse on first submission, 100% of completed agent runs must appear in telemetry, and no completed run may remain unaccounted for after two minutes.
4. **Require a large workflow gain, not parity.** Relative to legacy, the candidate must reduce median Director orchestration actions by at least 30% and either reduce median accepted-change elapsed time by at least 20% or reduce measured provider consumption by at least 20%, with no more than a 10% regression on either other axis. Reviewer active share must be at most 25%, the threshold already chosen before further batching work (`roster/wo14b-shakedown-punch-list.md:45`).
5. **Require unique quality evidence.** Seed defects and dual-blind adjudication must show that the retained cross-family or deterministic layer catches at least one material defect missed by the legacy fresh-reviewer path, without increasing false-positive major findings. If it does not, keep cross-vendor review as an on-demand option rather than part of the harness definition.
6. **Capture the whole bill.** Include actual Codex engine usage, not only Haiku launcher usage, and report cost per accepted change. A result with missing OpenAI usage, mixed pre/post-fix tickets, or manually inferred pool depletion is inconclusive and therefore fails this last-chance gate.

These thresholds are intentionally hard. A system with this much code and owner attention must win materially, not merely stop malfunctioning.

## STOPPING RULE

Stop 2.0 immediately and port the KEEP/PORT subset to legacy if any one of the following occurs during the frozen matched trial:

- A harness defect blocks or loses an otherwise valid run, serves the wrong model, allows unowned work, corrupts/changes the tested tree outside the work order, or requires reinstall/restart/re-pin.
- Any required comparison field is unavailable, including actual cross-vendor usage, completion state, acceptance result, or adjudicated review evidence. Missing evidence is a failed harness outcome, not permission for another instrumentation revision.
- After the full matched set, any operational, workflow-gain, review-share, or quality threshold above is missed.
- The candidate is only competitive after adding another state machine, taxonomy, retry layer, or close phase.

If all gates pass, keep only the slim tested layer; do not reactivate the deleted Router/Quartermaster/ticket architecture. If they do not pass, there is no fourth interpretation to explore. The few demonstrated advantages already have a direct port path.

## UNCERTAIN

- There is no matched legacy-run ledger, so this audit cannot estimate a causal speed, quality, or cost delta. The design's strongest comparative claim remains untested.
- The live ledger spans a period of active fixes and mixed configuration. It is excellent evidence of repair burden but not a clean estimate of post-2.5 steady-state behavior (`plans/cross-compare/agent-role-architecture/STATUS.md:862-907`).
- “Active time” is summed across overlapping tickets, the dollar values are list-price proxies rather than a bill, and actual Codex engine usage is absent (`tools/orchestra-ledger-report.js:1-23`, `tools/orchestra-ledger-report.js:386-401`).
- Anomaly rows include expected intermediate/refused states, and some `RESOLVED` work may have been intentionally left unclosed. The high counts establish lifecycle friction, not 136 distinct defects.
- Review findings are not linked to downstream escaped defects or an adjudicated legacy control. The real findings prove independent review has value; they do not prove 2.0 review has greater marginal value than a fresh legacy reviewer.
- This audit did not inspect `PiratePartyPals` or validate the product quality of the delivered changes, as required by the work order. It therefore does not infer that harness-frustrated tasks produced bad game code.
- There is no direct A/B evidence here for every named frontier model family. The conclusion concerns this implementation's demonstrated mechanics, not a claim that frontier models never benefit from structure.
